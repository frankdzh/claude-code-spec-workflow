# “需求分析师”代理：设计与集成方案

## 1. 概述

### 1.1. 问题背景：垃圾进，垃圾出 (Garbage In, Garbage Out)

自动化工作流的成功，高度依赖于其输入指令的质量。如果提供给后续开发或测试代理的任务描述是模糊、不完整或有歧义的，那么无论这些代理本身多么强大，其产出结果的质量和可靠性都将大打折扣。这直接导致了需要更多的人工干预和返工，削弱了自动化的核心价值。

### 1.2. 解决方案：前置的“指令质量门禁”

为了从根源上解决此问题，我们提议在工作流中引入一个全新的角色——**“需求分析师”代理 (Requirements Analyst Agent)**。它的核心职责是在自动化执行开始**之前**，对 `tasks.md` 文件进行一次深入的、智能化的“预检（Pre-flight Check）”或“掉毛测试（Linting）”。

此方案的本质，是将软件工程中“代码质量控制”的理念，前移到了“指令质量控制”的阶段，从而构建一个强制性的“指令质量门禁”。

---

## 2. 方案设计：独立的验证步骤

为了保证工作流的灵活性、可控性和透明度，我们将“需求分析师”设计为一个独立的、需要人工启动的步骤，而不是将其与 `spec-create` 命令合并。

### 2.1. 新增核心命令: `spec-validate`

- **命令**: `spec-validate <spec-name>`
- **职责**: 调用“需求分析师”代理，对指定的 `tasks.md` 文件进行审查。
- **执行流程**:
    1.  系统读取指定的 `tasks.md` 文件内容。
    2.  将内容提交给“需求分析师”代理，其核心提示（Prompt）应指导它检查以下方面：
        -   **清晰性与模糊性**: 任务描述是否清晰、无歧义？
        -   **完整性与上下文**: 是否缺少执行任务所必需的信息（如文件名、依赖项）？
        -   **原子性与范围**: 任务是否足够小且目标单一？
        -   **可执行性**: 任务是否是具体、可操作的编码或技术任务？
    3.  代理返回一份“问题报告”。
    4.  `spec-validate` 命令根据报告结果决定其退出状态：
        -   **若有问题**: 在终端显示报告，并以**失败状态**退出。
        -   **若无问题**: 显示成功信息，以**成功状态**退出，并在该Spec的内部目录（如 `.claude/specs/<spec-name>/`）中创建一个成功标记文件（如 `.validation-passed`）。

### 2.2. 调整现有命令: `spec-orchestrate`

- **核心调整**: 增加“前置守卫（Guard Condition）”。
- **实现逻辑**: 在 `spec-orchestrate` 命令的执行逻辑最开始，必须检查是否存在 `.validation-passed` 标记文件。如果不存在，则立即终止执行，并提示用户必须先成功运行 `spec-validate`。

### 2.3. 调整后的用户工作流

原始的“创建->执行”两步走，将升级为更严谨的“创建->验证->执行”三步走模式：

1.  **`spec-create <spec-name>`**: （无变化）生成 `tasks.md`。
2.  **`spec-validate <spec-name>`**: （新步骤）用户主动调用此命令进行验证。
    -   如果失败，用户需根据报告**手动修改 `tasks.md`**，然后**重新运行验证**，直至通过。
3.  **`spec-orchestrate <spec-name>`**: （有前置条件）只有在验证通过后，此命令才能成功启动。

---

## 3. 设计哲学：为何分离，而非合并？

将验证步骤设计为独立的命令，是基于对人机协作效率、灵活性和控制权的深思熟虑，而非仅仅追求最高程度的自动化。这赋予了人类用户四项宝贵的权力：

| 权力 | 描述 |
| :--- | :--- |
| **1. 审查“审查者”的权力** | 人类用户保留了对“需求分析师”代理判断的最终否决权。如果AI的质疑不合理，用户可以选择忽略，并通过强制执行等方式绕过验证，避免陷入与AI无谓的“较劲”中。 |
| **2. 探索性工作的权力** | 支持迭代式、非线性的工作模式。用户可以自由地起草和修改 `tasks.md`，而不被一个时刻运行的、强制性的验证流程所干扰。只在自己认为合适的时机，才主动触发验证。 |
| **3. 成本控制的权力** | “需求分析师”代理的调用是有成本的。分离的设计允许用户在本地多次修改后，只为最终的成熟版本支付一次验证成本，而不是在每次微调后都自动触发。 |
| **4. 流程透明的权力** | 将工作流分解为原子性的、单一职责的命令，极大地提升了系统的透明度和可调试性。当流程失败时，可以非常清晰地定位到是“生成”、“验证”还是“执行”环节出了问题。 |

## 4. 结论

将“需求分析师”作为一个独立的、强制性的验证步骤，是一种在“自动化效率”与“人类控制权”之间取得精妙平衡的成熟设计。它将一个建议性的“好习惯”固化为一个可靠的“质量门禁”，在不牺牲开发者主导权和灵活性的大前提下，从根本上提升了整个自动化工作流的可靠性和最终产出质量。

这种“生成 -> 审查 -> 执行”的模式，更贴近成熟的软件工程实践，也建立了一种更健康、更可持续的人机协作关系。
