# 面向 AI 驱动开发的动态 TDD 策略

## 1. 核心挑战：在专家经验与自动化之间取得平衡

对于一位经验丰富的开发者来说，测试驱动开发（TDD）并非总是一个刻板的、微观的流程。他们会利用经验和直觉来“拉伸”TDD 循环的跨度，例如一次性编写多个测试或整个功能，然后在运行测试，以此在保证质量的前提下优化开发速度。

AI 目前缺乏这种直觉，因此需要一种更结构化的方法。我们面临的挑战是，如何构建一个系统，既能避免因对每个任务都采用最严格的 TDD 流程而导致的效率低下，又能确保 AI 开发的可靠性——这是纯粹依赖直觉的方法无法为 AI 保证的。

解决方案是采用一种 **动态 TDD 粒度 (Dynamic TDD Granularity)** 策略。在该策略下，AI 将在人类的监督下，根据对任务风险和复杂性的评估，来选择合适的 TDD 循环“跨度”。

---

## 2. 策略详解：动态 TDD 粒度

我们引入一个全新的工作流，其中 AI 不仅将功能分解为任务，还会对每个任务组进行风险评估，以指定三种 TDD 策略中的一种。

### 第一阶段：在 `spec-create` 中进行风险评估

任务生成过程得到增强，能够根据风险对任务进行分类。

**实现方式：** 为生成任务的 Agent 修改提示（Prompt），加入以下指令：
> “为每个功能分解任务。然后，评估每个功能单元的复杂性和风险，并指定以下三种 TDD 策略之一：`[GRANULARITY:STRICT]`、`[GRANULARITY:STANDARD]` 或 `[GRANULARITY:RELAXED]`。”

#### TDD 粒度级别：

**A. `[GRANULARITY:STRICT]` (严格 TDD)**
- **适用场景：** 高风险或高复杂度任务（例如：核心算法、支付处理、复杂的状态管理）。
- **核心思想：** 最大化安全与验证。
- **任务分解示例：**
  ```markdown
  - [ ] 1. **(RED)** 为核心计算功能编写一个失败的单元测试。
  - [ ] 2. **(GREEN)** 编写最精简的实现代码，以使上一步的测试通过。
  - [ ] 3. **(REFACTOR)** 重构实现代码与测试，确保其清晰高效，并保证测试仍然通过。
  ```

**B. `[GRANULARITY:STANDARD]` (标准 TDD)**
- **适用场景：** 中等风险、标准功能（例如：CRUD 接口、UI 表单组件）。
- **核心思想：** 在安全和效率之间取得平衡，贴近许多开发者的实际做法。
- **任务分解示例：**
  ```markdown
  - [ ] 1. **(TEST & IMPLEMENT)** 为新的 API 接口编写所有必要的单元测试，然后实现接口逻辑，使所有测试一次性通过。
  - [ ] 2. **(REFACTOR)** 重构接口及其测试。
  ```

**C. `[GRANULARITY:RELAXED]` (宽松 TDD / 测试后置)**
- **适用场景：** 低风险、简单的任务（例如：UI 文案修改、CSS 样式调整、简单的配置更新）。
- **核心思想：** 对于那些琐碎的、几乎不可能出错的修改，最大化开发速度。
- **任务分解示例：**
  ```markdown
  - [ ] 1. **(IMPLEMENT & TEST)** 实现所需的 CSS 样式更改，并编写一个快照测试来验证视觉输出。
  ```

### 第二阶段：在 `spec-orchestrate` 中实现自适应编排

编排器（Orchestrator）需要升级，以理解并执行这些不同的 TDD 策略。它会解析每个任务组的 `[GRANULARITY]` 标签，并相应地调整其执行和验证逻辑。

**实现方式：** 编排器的核心循环将实现一个 switch 逻辑：

```typescript
for (const taskGroup of taskGroups) {
  const granularity = parseGranularity(taskGroup);

  switch (granularity) {
    case 'STRICT':
      await executeStrictTDD(taskGroup);
      break;
    case 'STANDARD':
      await executeStandardTDD(taskGroup);
      break;
    case 'RELAXED':
      await executeRelaxedTDD(taskGroup);
      break;
  }
}
```

- **`executeStrictTDD`:** 遵循完整的“红 -> 验证失败 -> 绿 -> 验证通过 -> 重构 -> 验证通过”循环。
- **`executeStandardTDD`:** 执行“测试与实现”任务，然后验证所有测试是否通过。如果失败，则进入修复循环。接着执行重构步骤，并在完成后再次验证。
- **`executeRelaxedTDD`:** 执行“实现与测试”任务，然后验证所有测试是否通过，如果失败则进入修复循环。

## 3. 平衡之道：人机协作 (Human-in-the-Loop)

实现效率与可靠性真正平衡的关键，在于无缝的人机协作。

1.  **可配置的默认策略：** 项目的 `spec-config.json` 文件中可以包含一个 `defaultTddGranularity` 设置（值为 `STRICT`、`STANDARD` 或 `RELAXED`）。这使得团队可以设定一个符合其项目质量标准的基线策略。

2.  **人类审核与覆盖：** 生成的 `tasks.md` 文件本身就是一份可供审核的计划。高级开发者可以快速浏览 AI 提议的任务和粒度级别。如果他们不同意 AI 的风险评估——例如，他们知道某个看似简单的任务实则暗藏玄机——他们可以直接在 `.md` 文件中**手动修改** `[GRANULARITY:RELAXED]` 为 `[GRANULARITY:STRICT]`。编排器将忠实地执行经过人类最终确认的计划。

---

## 4. 总结：通往平衡的 AI 开发之路

| 策略 | 实现方式 | 核心价值 |
| :--- | :--- | :--- |
| **动态粒度** | AI 评估风险，在 `STRICT`、`STANDARD` 和 `RELAXED` 三种 TDD 策略中进行选择。 | **效率：** 模拟专家直觉，让流程的开销与任务的复杂度相匹配。 |
| **人机协作** | 开发者可以直接在 Markdown 文件中审核并覆盖 AI 的策略选择。 | **可靠性：** 利用人类经验来纠正 AI 的认知盲点，提供最终的质量控制。 |
| **项目级配置** | 可以为整个项目设置一个默认的 TDD 策略。 | **适应性：** 使 AI 的行为与项目的特定质量和速度要求保持一致。 |

这种混合模式在赋予 AI 高效工作能力的同时，确保了人类的专业经验能够提供最终的保障，从而实现了速度与可靠性的强大结合。
