# 多智能体TDD策略：需求分析与设计方案

## 1. 概述

### 1.1. 问题陈述
当前，本工作流中的TDD（测试驱动开发）任务由一个通用的AI代理执行。尽管该代理可以被指示遵循TDD流程，但其本质上是一个“自我监督”的独角戏。这种模式缺乏内在的制衡机制，在处理复杂的、高风险的任务时，可能会出现以下问题：
- **流程简化**: AI可能为了尽快完成任务而无意识地“抄近路”，例如编写一个过于简单的、无法覆盖真实边界情况的“失败测试”。
- **思维盲点**: 单个代理难以发现自身的逻辑或设计缺陷，就像开发者很难完美地审查自己的代码。
- **提示过载**: 要求单个代理同时扮演“测试设计者”、“代码实现者”和“质量审查员”三个角色，使其提示（Prompt）变得异常复杂，增加了出错的概率。

### 1.2. 目标
为了从根本上提升TDD任务的执行质量和可靠性，我们提议引入一个**多智能体协作模型**。其核心目标并非简单地“模拟”TDD流程，而是**在系统中构建一种程序化的、建设性的对抗与制衡机制**，从而确保每一步产出的质量，最终实现更可靠、更健壮的自动化代码生成。

---

## 2. 核心方案：“红-绿-重构”三位一体模型

我们拒绝采用简单的“开发者-测试员”模型，因为它本质上是“测试后置”，与TDD“测试先行”的核心哲学相悖。我们提出一个真正体现TDD精神的、按**阶段**划分职责的多智能体方案。

### 2.1. 方案构想
对于`[GRANULARITY:STRICT]`级别的任务，`spec-orchestrate`（编排器）将启动一个由三个专业化代理协作的微流程：

1.  **“红”代理 (The Red Agent - The Challenger)**
    -   **单一职责**: 编写一个失败的测试。
    -   **核心任务**: 深入理解需求，编写一个能够精确描述该需求、覆盖边界情况、且在当前代码库中**必然会失败**的单元测试。它扮演“出题人”的角色。
    -   **验证门禁**: 编排器必须验证其产出的测试能够运行，且**结果必须是失败**。

2.  **“绿”代理 (The Green Agent - The Solver)**
    -   **单一职责**: 用最少的代码让测试通过。
    -   **核心任务**: 在“红”代理给出的“考题”（失败的测试）框架内，编写最简洁、最直接的功能代码，使其通过测试。它扮演“解题人”的角色。
    -   **验证门禁**: 编排器必须验证此前失败的测试在本次修改后**结果必须是全部通过**。

3.  **“重构”代理 (The Refactor Agent - The Polisher)**
    -   **单一职责**: 在功能不变的前提下，优化代码质量。
    -   **核心任务**: 对“绿”代理提交的代码和（或）测试代码进行重构，提升其可读性、效率和架构合理性。
    -   **验证门禁**: 编排器必须验证所有测试在重构后**结果必须依然全部通过**。

### 2.2. 方案优势：为何“得”远大于“失”

此方案的优势远不止是流程模拟，它构建了一套精妙的内在机制。

| 优势 | 描述 |
| :--- | :--- |
| **内在制衡机制** | 通过“红-绿”代理之间的“出题-解题”关系，形成了一种建设性的对抗。这种程序化的制衡，迫使代码实现必须严格遵循测试所定义的设计契约，能发现单个代理因“思维盲点”而忽略的设计缺陷。 |
| **思维脚手架** | 每个代理的职责都极其单一，极大地降低了AI的“认知负荷”。“红”代理专注于测试设计，“绿”代理专注于问题解决，“重构”代理专注于代码美学。这种专注使每一步的产出都更深入、更专业。 |
| **深度专业化** | 我们可以为每个代理设计高度优化的、截然不同的提示。例如，“红”代理的提示可以富含测试设计的最佳实践，“绿”代理的提示则专注于编码规范和算法效率。这使得整个系统的“专业技能总和”远超单个通用代理。 |

### 2.3. 成本与风险管理

该方案的主要缺点是增加了执行时间和API调用成本。但这部分成本是可控且值得的。

| 弊端/风险 | 缓解策略 |
| :--- | :--- |
| **执行成本高昂** | 1. **选择性应用**: 此方案仅用于最高风险、最核心的`STRICT`任务，是一种“好钢用在刀刃上”的策略。<br>2. **模型分级**: 可为不同阶段配置不同成本和能力的AI模型（如“红”代理使用快速模型，“重构”代理使用顶级模型），在保证质量的同时优化总成本。 |
| **编排逻辑复杂** | 这是为了追求更高质量所必须付出的工程投资。一个健壮的、可管理状态的编排器是实现高级自动化工作流的基石。 |
| **代理协作失败** | “红”代理可能写不出好的失败测试，或“绿”代理无法修复。编排器需要设计重试和错误上报机制，在多次尝试失败后，将清晰的失败上下文报告给人类用户进行干预。 |

---

## 3. 结论与建议

将TDD流程从“单人独角戏”升级为“多方对手戏”，并非小题大做，而是从“能用”到“可靠”的战略性一步。它所引入的内在制衡与专业化分工，是保证复杂软件系统能够被高质量、可持续地自动化构建的关键。

**我们强烈建议采纳“红-绿-重构”三位一体模型作为本工作流在TDD方向上的核心演进方案。**

建议分阶段实施：
1.  **第一阶段**: 实现核心编排逻辑，支持三个代理的顺序调用和状态验证。
2.  **第二阶段**: 为三个代理分别设计和优化其专属的、高度专业化的提示。
3.  **第三阶段**: 引入模型分级和更精细的错误处理机制，以优化成本和鲁棒性。
